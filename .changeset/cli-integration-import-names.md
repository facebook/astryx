[feat] `astryx doctor integration validate` now also lists, from source and without a build, an import that names something its module does not export, as notes on its result (`data.notes`, each with its fix in the message). The notes are listed only: neither `doctor integration validate` nor `astryx integration check --strict` counts them or fails on them in 0.7.3, and they become failing warnings in the next minor release, so fix them now. It notes a component's import (the doc's `import`, or the one the CLI derives when the doc has none) that leads to a module that does not export the component, naming the subpath that does or the `exports` entry to add; a component example or a template that imports a name the package does not export; and a template source with no default export (`astryx template` still copies it, but its public import and anything that renders it get nothing), suggesting an exported PascalCase function, class or `const` (never a hook such as `useAccount`, a helper such as `formatBalance`, an ALL-CAPS constant or a type; with none, the fix stays generic). A name is judged only when a file the `exports` entry names is there to read in full: `export *` is followed, cycles included; a built module's declaration file (`x.d.ts` beside `x.js`, and the `.d.ts` files a declaration file's `export *` names) is read for the types it exports; and `export import Alias = Inner.Value` counts as an export. TypeScript source resolves a `./x.js` specifier to `./x.ts`, and a declaration file that is a module exports every top-level declaration unless it has an export list, `export *`, `export =` or a default export of an expression, as TypeScript does. Whatever the reader does not fully model is listed under `unchecked` in the `publicImports` report instead of as a note: a file the `exports` entry names that does not exist yet, a module whose list cannot be read in full (CommonJS, `export *` from another package), a declaration file with no import or export (a global script), every name it would report (other than a component doc's own component, which is always judged) while a TypeScript file in the package (outside `node_modules`) has a parsed `declare module` block for a relative path or the package's own name or a subpath of it, since such an augmentation can add names to that module (the reason names that file; `declare global`, a wildcard spec such as `'*.css'`, another package's name and a `declare module` in a comment do not count, and a file with `declare module` in its text that cannot be parsed counts), or a name missing from a JavaScript module with no declaration file, which may be a type.
