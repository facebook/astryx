[feat] `astryx doctor integration validate` now lists, from source and without a build, what an integration package tells apps to import that they cannot import, in a new `publicImports` report on its result (`{status: 'checked', findings, unchecked}`). The findings are listed only: neither `doctor integration validate` nor `astryx integration check --strict` counts them or fails on them in 0.7.3, and they become failing warnings in the next minor release, so fix them now. It lists a component's import (the doc's `import`, or the one the CLI derives when the doc has none) or a template's public import whose subpath package.json `exports` does not declare (a missing key, a key whose only conditions an ES module import does not load, such as `require` or `types`, an `exports` that is a single string, a wildcard that does not match) or that names another package; a component example that imports a subpath the package does not declare; and a template that imports a relative path outside the templates root, or a path its own package or Core does not export. Each finding names the fix, such as the exact `exports` entry to add. Only the declared subpath is judged, never the target file or the names it exports, so `exports` may point at build output that does not exist yet; wildcards and condition objects with `import` or `default` pass, an `import type` statement accepts a `types`-only entry, and a package with no `exports` keeps its deep paths to files it ships. What it cannot judge (in a package with no `exports`, a deep path into build output not built yet, such as `dist/`; a template import of Core when `@astryxdesign/core` is not installed beside the package; every import of the package's own name when package.json has no `name`) is listed under `unchecked`, which `integration check` counts as not compared.
